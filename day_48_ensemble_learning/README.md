# Ensemble Learning: Voting, Bagging, Boosting, Stacking, and Blending

## Technical Scope

Ensemble learning combines multiple predictive models to produce a joint prediction. The central idea is that models with different errors, training samples, or learning strategies can provide complementary information.

An ensemble is not automatically better than its strongest component. Its value depends on component quality, error correlation, the aggregation rule, validation methodology, and the cost of incorrect predictions.

This implementation package covers five related methods:

- **Voting** combines predictions from independently trained models.
- **Bagging** trains models on bootstrap samples and aggregates their outputs.
- **Boosting** builds models sequentially, directing attention toward errors made by earlier learners.
- **Stacking** trains a meta-model on predictions generated by base models.
- **Blending** learns a combination using predictions on a separate validation partition.

The Python and JavaScript programs implement learning algorithms and aggregation. The C++ program models fraud-alert classification. The Java program separates predictive components from an enterprise decision policy. The PostgreSQL script stores experiment definitions, component relationships, predictions, and evaluation results.

## How the Methods Differ

| Method | How models are trained | How outputs are combined | Main consideration |
|---|---|---|---|
| Voting | Usually independently | Majority vote or weighted vote | Models should provide useful and complementary predictions |
| Bagging | Independently on bootstrap samples | Vote or average | Reduces instability, especially for high-variance learners |
| Boosting | Sequentially, with later rounds responding to earlier errors | Weighted combination | Can be sensitive to noise and mislabeled observations |
| Stacking | Base models are trained first; a meta-model follows | Learned meta-model | Requires leakage-safe out-of-fold predictions |
| Blending | Base models are trained on training data | Learned combination using held-out validation predictions | Consumes validation data that could otherwise be used for training |

### Voting

Voting does not require a new learning algorithm for the combination stage.

For binary hard voting, the ensemble predicts the class receiving the most votes. Weighted voting assigns a coefficient to each model:

\[
\hat y =
\begin{cases}
1 & \text{if } \sum_i w_i \mathbf{1}(\hat y_i=1) >
\frac{1}{2}\sum_i w_i \\
0 & \text{otherwise}
\end{cases}
\]

The implementation resolves ties deterministically. Weights should reflect evidence from validation data rather than arbitrary preferences.

Soft voting averages predicted probabilities. Probability averaging can retain confidence information that hard voting discards, but it assumes that the probabilities are sufficiently meaningful and comparable. Poorly calibrated models can dominate a combination despite having inaccurate confidence estimates.

### Bagging

Bootstrap aggregation generates multiple training datasets by sampling the original observations with replacement. A bootstrap sample typically contains the same number of rows as the original training set, although some original observations appear multiple times and others are omitted.

Each model is fitted independently. Classification commonly uses majority voting, while regression commonly uses averaging.

Bagging can reduce variance when component errors differ across bootstrap samples. It does not necessarily reduce systematic bias, and identical or highly correlated models may receive little benefit from aggregation.

The Python and JavaScript implementations train decision stumps on independently sampled datasets. The C++ case study uses the same basic bootstrap principle for transaction-risk predictions.

### Boosting

Boosting combines weak learners in a sequence. AdaBoost assigns more relative weight to observations that earlier learners misclassified.

For a binary weak learner with weighted error \(\epsilon_t\), the learner's contribution is:

\[
\alpha_t = \frac{1}{2}
\ln\left(\frac{1-\epsilon_t}{\epsilon_t}\right)
\]

The algorithm updates observation weights according to whether each prediction is correct, then normalizes them before the next round.

A learner with weighted error at or above one half provides no useful improvement under the standard binary AdaBoost formulation. A perfect learner needs special handling because the logarithmic expression becomes unbounded.

Gradient boosting follows a different formulation: each new learner approximates a direction that improves the chosen loss function. It is not simply another name for AdaBoost.

Boosting can achieve strong predictive performance, but excessive rounds, noisy labels, or poorly controlled learner complexity can produce overfitting. The included implementations use shallow decision stumps to make the sequential weighting mechanism explicit.

### Stacking

Stacking learns how to combine base-model predictions rather than assigning all models a fixed vote.

A simplified classification workflow is:

1. Divide the training data into folds.
2. Train each base model without one fold.
3. Predict the held-out fold with that model.
4. Assemble the out-of-fold predictions into a meta-feature matrix.
5. Train the meta-model on that matrix and the original training labels.
6. Refit the base models on the complete training partition.
7. Generate base predictions for unseen observations and pass them to the fitted meta-model.

For example, the meta-model may receive the probability from logistic regression and the probability from a random forest. It can learn that one model is more informative in particular regions of the feature space.

The critical requirement is that each out-of-fold prediction must come from a model that did not train on that observation. Training a meta-model on in-sample predictions can leak information and make its apparent performance misleading.

Preprocessing is part of this rule. Imputation, scaling, feature selection, and other learned transformations must be fitted within the relevant training fold.

The Python program includes an out-of-fold prediction workflow. Its simplified demonstration combines base-model class predictions; a production stacker would ordinarily preserve probabilities or other informative outputs and fit a dedicated meta-model.

### Blending

Blending resembles stacking, but it uses a dedicated held-out validation set to train the combination model.

Base learners fit on the training partition predict the validation partition. A combiner is fitted on those predictions and validation labels. The final test partition remains untouched until evaluation.

Blending is easier to implement because it does not require generating predictions across multiple folds. Its main trade-off is that the validation observations are not available for fitting the base learners in the initial training phase.

The JavaScript implementation selects a weighted probability combination by minimizing validation log loss over a grid of weights. The final test loss is calculated separately.

## Python Implementation

The Python script uses only the standard library.

### Logistic regression

`LogisticRegression` implements batch gradient descent with L2 regularization. Its predicted probability is the sigmoid of a weighted feature sum. The implementation validates the feature dimensions and binary labels before fitting.

### Decision stumps

`DecisionStump` searches feature thresholds and the two possible assignments of binary labels to the threshold's left and right sides. It minimizes weighted classification error.

The same weak learner supports multiple ensemble mechanisms. In bagging, all training rows in a bootstrap sample have equal weights. In AdaBoost, the training weights change after each round.

### Bagging and AdaBoost

`BaggingClassifier` uses a seeded random generator to create reproducible bootstrap samples. It trains independent stumps and combines their labels using a majority vote.

`AdaBoostClassifier` repeatedly fits a weighted stump, calculates its weighted error, determines its coefficient, and updates the sample weights. It stops when a learner is unhelpful or perfectly classifies the training set.

The boosting probability transformation is a monotonic transformation of the weighted margin. It is not guaranteed to produce calibrated probabilities.

### Evaluation and out-of-fold predictions

`accuracy` measures the proportion of correctly classified examples. `log_loss` evaluates the quality of probabilistic predictions and penalizes confident errors.

The train/test split ensures that final evaluation observations are excluded from fitting. The out-of-fold helper generates training-set predictions from models that exclude each prediction's observation.

For reliable comparisons, model selection, threshold selection, feature preprocessing, and ensemble-weight selection must not use the final test labels.

## JavaScript Implementation

The JavaScript file uses Node.js and the standard `assert` module. It illustrates how model composition can be organized around executable classes and explicit method contracts.

`LogisticModel` estimates probabilities through gradient descent. `Stump` implements weighted threshold search. `BaggingEnsemble` independently samples training rows, while `AdaBoostEnsemble` updates the observation weights sequentially.

The seeded generator makes the experiment reproducible without external packages. `hardVote` validates that every model provides the same number of binary predictions and that voting weights are finite and nonnegative.

The blending function searches candidate weights using validation log loss. It then applies the selected combination to test predictions. The base models must be trained without the final test data for this evaluation to remain meaningful.

## C++ Case Study: Payment Fraud Alerts

The C++ program models a payment-risk classification pipeline.

### Feature representation

The `Transaction` structure contains transaction amount, account age, recent transaction velocity, and the target label.

The `encode` function validates records and applies logarithmic transformations to numeric features. Scaling can improve optimization and prevent large numerical magnitudes from dominating a model.

The dataset generator creates a deterministic synthetic transaction sample. Its labels are produced from a noisy rule, so the data represents a controlled experiment rather than real fraud statistics.

### Bagging architecture

`BaggingModel` draws a bootstrap sample for every estimator. Each stump is fitted independently. Predictions are combined by majority vote, with ties resolved as the negative class.

### Boosting architecture

`AdaBoostModel` maintains a weight for every training observation. It fits a stump, measures weighted classification error, calculates the learner coefficient, and updates the observation weights.

The implementation rejects invalid configurations and stops when a weak learner cannot improve on chance. It also checks that the weight-normalization factor is finite and positive.

### Decision policy

`WeightedVotingPolicy` combines bagging and boosting outputs. Its coefficients are validated at construction time, and predictions outside the binary label domain are rejected.

The policy demonstrates a distinction between a predictive model and the system that consumes its predictions. A production fraud service would also need a carefully calibrated probability threshold, precision and recall analysis, false-positive cost estimates, latency controls, and monitoring for changes in fraud behavior.

## Java Implementation: Enterprise Risk Decisions

The Java program uses domain-specific records, interfaces, enums, and service classes to separate model behavior from operational decisions.

### Domain model

`Payment` validates the transaction identifier and numeric features. Its `features` method produces the transformed feature vector used by the predictive components.

`Prediction` represents one model's probability and identity. Its constructor rejects invalid probability values and missing model names.

`ProbabilisticModel` defines a common contract for training and prediction. This allows the decision service to combine heterogeneous models without depending on their internal algorithms.

### Model implementations

`LogisticModel` estimates probabilities using gradient descent and regularization.

`ThresholdModel` derives median feature thresholds from its training partition. It produces a rule-based risk score using amount, account age, and recent transaction velocity. This model is intentionally different from logistic regression, illustrating how heterogeneous components can supply different information to an ensemble.

### Decision service

`VotingPolicy` computes a weighted probability average and validates its weights. It clones the supplied weight array to prevent later modification of the original array from changing the policy.

`DecisionService` converts the combined risk score into `APPROVE`, `REVIEW`, or `BLOCK`. The review and block thresholds must be ordered and lie within the valid probability range.

The program reserves training, validation, and test partitions. The validation partition is separate from the final test partition, while model fitting uses only the training partition.

The illustrative thresholds are fixed demonstration values. A deployed system would select them using an explicit business objective, validation data, expected losses, and operational review capacity.

## PostgreSQL Data Model

The SQL script uses PostgreSQL-compatible DDL, JSONB, identity columns, check constraints, foreign keys, indexes, views, and transactions.

### Relational entities

| Table | Responsibility |
|---|---|
| `data_observations` | Stores dataset identifiers, binary labels, and feature payloads |
| `ensemble_experiments` | Defines the ensemble type, task, validation strategy, and random seed |
| `model_artifacts` | Records model algorithms, versions, training datasets, and hyperparameters |
| `ensemble_components` | Connects models to experiments with roles and aggregation weights |
| `experiment_split` | Records the training, validation, or test assignment of each observation |
| `ensemble_predictions` | Stores base, meta, and final ensemble predictions |
| `evaluation_metrics` | Records partition-specific metrics and sample counts |

Foreign keys preserve relationships between experiments, models, observations, and predictions. Unique constraints prevent duplicate component positions, duplicate model versions, repeated experiment assignments, and duplicate metric records for the same experiment and partition.

Check constraints restrict ensemble types, component roles, partition names, binary labels, nonnegative weights, and probability values. These checks prevent invalid records from entering the relational model through ordinary SQL operations.

### Experiment configuration and components

The experiment registry distinguishes the five ensemble methods. Component roles identify ordinary base learners, boosting weak learners, and meta-models.

The `aggregation_weight` field represents a configured component weight. It does not automatically implement model inference. The application that performs predictions remains responsible for applying the correct aggregation algorithm.

For example, a boosting implementation must account for learner coefficients, while a stacking implementation must pass base predictions into the fitted meta-model. These mechanisms should not be reduced to the same database query.

### Partition integrity

`experiment_split` associates each observation with one partition per experiment. Its primary key prevents an observation from being assigned to training and test partitions simultaneously within the same experiment.

The sample partitions are illustrative. In a real evaluation, the assignment process should also preserve temporal ordering where appropriate, account for repeated entities, and prevent related records from crossing partition boundaries when doing so would leak information.

### Prediction provenance

`ensemble_predictions` identifies the experiment, observation, model, stage, probability, and predicted class. This allows analysts to compare base-model behavior with ensemble outputs and investigate disagreement.

The sample prediction rows are explicitly illustrative rather than the output of a trained model. They demonstrate the storage structure and database constraints.

### Evaluation and reporting

`evaluation_metrics` stores metrics separately by partition. The comparison view supports querying performance by ensemble type and dataset partition.

The prediction summary view reports counts and mean predicted probabilities. Such aggregates help inspect score distributions but do not replace accuracy, precision, recall, calibration, or loss calculations against trusted labels.

The transaction at the end demonstrates an atomic metric upsert. The commented invalid inserts show how constraints reject unsupported ensemble types, out-of-range probabilities, and negative component weights.

## Evaluation Metrics

Accuracy is the fraction of observations classified correctly. It is easy to interpret but can be misleading when one class is much more common than the other.

Precision measures the fraction of positive predictions that are correct. Recall measures the fraction of actual positive observations that the model detects. F1 combines precision and recall through their harmonic mean.

Log loss evaluates predicted probabilities rather than only predicted labels:

\[
L = -\frac{1}{N}\sum_{i=1}^{N}
\left[y_i\log(p_i)+(1-y_i)\log(1-p_i)\right]
\]

A model can achieve good classification accuracy while producing poorly calibrated probabilities. For blending and soft voting, probability quality matters because the aggregation rule uses the numerical scores directly.

ROC-AUC measures ranking quality across thresholds. Precision-recall analysis can be especially informative when positive examples are rare.

No single metric establishes that an ensemble is appropriate. Selection should reflect the prediction task, class balance, decision costs, and the reliability of the evaluation procedure.

## Failure Modes and Engineering Considerations

### Correlated component errors

Adding multiple similar models does not guarantee a better ensemble. If they make the same errors, aggregation may provide little improvement. Component diversity is useful when it adds predictive information without sacrificing too much individual quality.

### Data leakage

Leakage occurs when information from evaluation observations influences training, preprocessing, feature selection, threshold tuning, or meta-model construction. Stacking is particularly sensitive to leakage because the meta-model learns directly from base-model predictions.

### Overfitting validation data

Repeatedly adjusting weights against the same validation set can overfit the blending strategy. A separate test set or nested validation procedure is needed to estimate performance after model selection.

### Class imbalance

Majority voting can favor the common class. Evaluation should consider minority-class recall, precision, class-specific error costs, and whether weighted training or threshold adjustment is justified.

### Probability calibration

Hard-voting outputs are labels, not probabilities. Boosting margins transformed through a sigmoid are not automatically calibrated. Calibration should be evaluated and fitted using data reserved for that purpose.

### Computational cost

Bagging often trains models in parallel because the bootstrap fits are independent. Boosting generally trains sequentially because later learners depend on earlier results. Stacking adds the cost of generating out-of-fold predictions, while blending needs a dedicated validation partition.

### Reproducibility and monitoring

Random seeds make experiments easier to reproduce, but reproducibility also depends on data versioning, preprocessing configuration, software versions, and consistent split definitions.

Production ensembles should retain component versions, input-data provenance, validation results, and prediction records. Monitoring should detect distribution changes, degraded component performance, unexpected disagreement, and shifts in false-positive or false-negative rates.

## Production Design Principles

- Fit preprocessing within each training fold when generating out-of-fold predictions.
- Preserve a final test set that does not influence model selection or ensemble weights.
- Compare the ensemble with each component model to verify that aggregation produces measurable value.
- Use probability averaging only when component scores have compatible meanings and adequate calibration.
- Treat boosting weights and stacking meta-features as algorithm-specific data, not interchangeable voting coefficients.
- Validate component identities, feature dimensions, probability ranges, and training-state requirements before inference.
- Evaluate decision thresholds against operational costs rather than optimizing accuracy alone.
- Store experiment configuration, component versions, split assignments, metrics, and prediction provenance so that results can be audited.
